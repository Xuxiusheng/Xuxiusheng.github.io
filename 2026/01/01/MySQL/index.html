MySQL基础

数据库模型

主流的数据库模型大致分为两类：结构化数据库和非结构化数据库，结构化数据库也叫做关系型数据库，存储的数据必须是表结构行列固定的结构化模式，一张表就是一个关系。非结构化数据库的约束就要小很多，可以存储二进制、音视频和字符串以及JSON等格式，天然支持横向扩展。

维度 结构化数据库 非结构化数据库
模型结构 结构化存储，具有固定行列的表格 非结构化存储
ACID属性 部分引擎支持ACID，提供强一致性访问 一般支持最终一致性
可扩展性 支持垂直扩展、读写分离、分库分表等，横向扩展需要做一定的性能牺牲 天然支持横向扩展，通过增加节点实现
查询语法 SQL 一般不同的非结构化数据库语法不同
概念 简称 定义
数据库 DB 信息的集合，是由数据库管理系统（DBMS）统一管理的数据集合。
数据库管理系统 DBMS 一种用于建立、使用、维护和管理数据库的大型软件系统，提供数据操作与控制功能。
数据库管理员 DBA 负责全面管理、维护、优化和控制数据库系统的专业人员。
数据库系统 DBS 由数据库（DB）、数据库管理系统（DBMS）、应用程序和数据库管理员（DBA）组成的整体系统。

范式 核心要求 解决的问题
1NF 列的原子性 确保基本结构,每一个字段都不可再分
2NF 消除部分依赖 每个关系必须有一个主键，所有属性必须完全依赖于主键，不能只依赖主键的一部分
3NF 消除传递依赖 所有属性直接依赖于主键，消除传递依赖

范式并非越高越好。更高级的范式意味着更多的表，当进行复杂查询时，就需要连接（JOIN）更多的表，这可能会降低查询性能。范式化是为优化写操作，减少数据冗余；反范式化是为优化读操作，减少连表Join

外键在当前的高并发分布式架构下尽量避免使用，因为会引起数据库级联更新风暴，在数据量规模较小的单体架构下推荐使用

存储过程

存储过程是一组完成特定功能的预编译的SQL语句集合。它类似于编程语言中的函数或方法。存储过程创建时被编译和优化存储在数据库服务器中，业务端使用时只需要指明存储过程名和传入数据，极大减少了网络传输流量，并且能够避免SQL注入。

存储过程不是银弹，具有双面性：

  • 正面性：预编译存储到数据库服务器，用户不需要重复传输相同的命令，减少网络流量，代码复用性强，能够避免SQL注入
  • 反面性：业务逻辑耦合在存储过程中，不方便调试；不同厂商的存储过程差异巨大； 高并发场景对可扩展性要求高，存储过程难以维护，无法做到灰度平滑发布，而且版本管理困难

SQL常用命令解析

Drop & Truncate & Delete

Drop用于删除表数据和表结构，属于DDL命令，MySQL的DDL命令即使在关闭隐式提交autocommit的情况下也会强制提交事务并立即生效，并且无法回滚，需要及时备份，该命令能够重置自增计数器

Truncate也属于DDL语句，和Drop类似，但是只会清空数据，不会删除表结构，立即生效，无法回滚，也会重置自增计数器，性能是三者中最好的

DELETE属于DML语句，删除部分或全部数据，保留表结构，性能是最差的，因为涉及到行级锁以及回滚段标记的重置，但是安全性最高，支持事务回滚

Group By & Order By

两者的执行顺序是先执行Group by分组聚合，再order by进行排序。之所以采用这个顺序是因为分组会改变数据的行列结构，聚合后会产生之前没有的列属性，order by可能会根据新属性排序。

GROUP BY使用HAVING过滤分组结果，WHERE 过滤的是“分组前的原始行”，HAVING 过滤的是“分组后的聚合结果”，两者的作用阶段不同

EXISTS & IN

详细区别参考EXISTS & IN

IN执行过程:

  1. 执行子查询，结果集（m条记录）存储在临时表中
  2. 主查询（n条记录）逐行遍历，遍历结果集查看当前记录字段值是否存在于结果集中
  3. 适合子查询结果集较小的情况，最差需要遍历m*n次（笛卡尔积逐行遍历寻找符合条件的行记录）

EXISTS执行过程:

  1. 逐行遍历主查询字段值
  2. 将当前字段值用于子查询（子查询有索引的话会很快）

适用场景总结:

  1. IN适用于子表行数较少的情况
  2. EXISTS适用于主查询结果集小且子查询关联字段有索引的情况

NOT IN命令无法利用索引，主查询与子查询计算笛卡尔积后逐行遍历查询，时间复杂度为O(mn)，NOT EXISTS依然按照EXISTS执行，时间复杂度为O(nlogm)

COUNT

执行速度：count(1)=count(星号) > count(索引字段，非主键索引) > count(主键)>count(非主键字段)

查询语句 扫描对象 对每一行的操作 性能开销
COUNT(*) / COUNT(1) 主键索引树 几乎无操作，不解析具体的行数据 最低
COUNT(主键) 主键索引树 需要从索引条目中取出主键值，多了一步读取数据的操作 较低，比 COUNT(*) 多一步解析动作
COUNT(索引字段) 可能扫描更小的二级索引树 读取字段，判断是否为 NULL。因为二级索引通常比主键索引小很多，I/O 效率更高 可能很快（如果二级索引很小），但每行需要检查 NULL
COUNT(非索引字段) 主键索引树 需要读取整行数据，然后从行数据中解析出该字段的值，再判断是否为 NULL 最高。因为要解析和读取最多的数据

MySQL基础架构

MySQL的整体架构可分为两部分：Server层和存储引擎，Server层负责操作数据之前的预处理工作，比如校验权限、生成执行计划等，存储引擎则负责实际的数据存储管理。

Server

所有跨存储引擎的功能都在Server层实现，如存储过程、触发器等。

连接器

连接器是MySQL Server层的第一个模块，负责处理客户端的连接请求，包括连接建立、身份验证以及会话管理等。MySQL采用长连接模式，如果长时间没有操作，会自动断开连接，wait_timeout控制断连时间，默认8小时，但是长连接在此期间会持续占用内存，有内存泄漏风险，如何解决？

  1. 定期断开长连接，清除占用内存（下次需要重新握手）
  2. 初始化连接，不需要重新建立连接，当前事务执行完后会释放占用的内存，恢复到初始状态

分析器

客户端连接发送的SQL语句，经过SQL接口后会被分发到分析器，验证SQL语句是否正确，以及将SQL语句解析成MySQL能看懂的机器码指令

优化器

优化器会根据CPU成本和I/O成本选择最优的执行计划，执行计划 是指一条 SQL 语句在经过 MySQL 优化器的优化后，具体的执行方式。通过EXPLAIN可以获取对应的执行计划，EXPLAIN并不会去执行命令，只是简单地获取执行计划。

比如，多表JOIN时，JOIN顺序重构；当有多个索引可用时，选择最合适的索引

这里介绍下EXPLAIN命令输出的几个关键字段：

列名 含义
select_type 查询类型：SIMPLE简单查询；PRIMARY嵌套查询中的外层查询；SUBQUERY嵌套查询中的子查询；UNIONUNION语句中UNION之后出现的查询；DERIVED出现在FROM之后的查询
type 查询执行的类型，const表示最多命中一行记录，常用于主键或唯一索引查询；eq_ref在连表查询时，后一张表的行记录只有一个与前一张表对应，常用于主键或唯一索引作为连表条件；ref使用普通索引作为查询条件；range常用于范围查询；index常用于全表扫描，不过扫描的是索引树；ALL用于全表扫描
possible_keys 表示 MySQL 执行查询时可能用到的索引
key 表示实际用到的索引
rows 预估命中的数据行
extra Using filesort使用了外部索引排序，没有用到索引树自身的排序；Using temporary使用了临时表；Using index使用了覆盖索引；Using index condition使用了索引下推；Using where使用了 WHERE 子句进行条件过滤，常表示没有命中索引查询

当type为index或者all，extra为where、filesort、temporary时，需要对命令语句进行优化，因为这几个常表示索引没有命中

查询缓存

MySQL Query Cache是用来缓存我们所执行的SELECT语句以及该语句的结果集，以KV的形式存储。但是查询缓存一般不建议启用，因为命中条件很苛刻：客户端版本、字符集类型等都要相同，一旦发生了写表操作，该表对应的缓存全部失效。非常不利于多些场景，在只读情况下可以考虑开启。建议使用分布式缓存替代。

执行器

负责执行优化器生成的执行方案

存储引擎

硬盘负责存储数据，存储引擎则负责管理数据，客户端与Server层交互，Server层通过执行器与存储引擎交互，存储引擎与硬盘数据交互，MySQL的存储引擎是基于表的，即可以为不同的表指定不同的存储引擎。

InnoDB逻辑空间结构
  • 表空间：表空间是InnoDB的逻辑结构的最高层，ibd文件就是表空间文件
  • Segment段：表空间包含多个段，包括数据段、索引段和回滚段
  • Extent区：一个段包含多个区，默认大小为1MB，为了保证页的连续性，InnoDB申请空间时往往连续申请多个区
  • Page页：页是InnoDB管理数据的最小单元，即使只访问一行数据，InnoDB也会将整个页加载进入内存

MySQL 存储引擎采用的是 插件式架构 ，支持多种存储引擎，存储引擎是基于表的，而不是数据库，可以针对表的类型设置不同的存储引擎。目前广泛采用的存储引擎是InnoDB，在InnoDB出现之前，MyISAM是主流的存储引擎，下面来对比下两者：

维度 InnoDB MyISAM
事务 事务型存储引擎，实现了ACID特性 不支持事务
崩溃恢复能力 redo和binlog结合实现崩溃后的数据恢复 不具备崩溃恢复能力
行级锁 支持行级锁 不支持行级锁，最大的粒度是表级锁
MVCC 支持 不支持
底层索引结构 聚簇索引 非聚簇索引
缓存机制 缓存数据页和索引页 只缓存索引页
COUNT(星)速度 慢，逐行扫描 快，有全局变量记录总行数
适用场景 写密集场景 读密集场景

MySQL索引

索引是一种用于快速查询和检索数据的数据结构，能够避免全表扫描。索引并不是银弹，会占用存储空间，而且检索需要回表查询数据。同时优化器生成执行计划需要时间。索引适合海量数据查询场景，在数据量较少的场景下不适合适用。

索引底层结构

维度 Hash 二叉查找树 AVL 红黑树 B树 B+树
优势 结构简单，查询速度快 理想最优时间复杂度为O(logn) 相比于二叉查找树，性能更加稳定，不会出现退化情况 降低了AVL树维护平衡的成本 B树属于多路平衡查找树，每个节点存储多个数据，树高更低，检索效率更好 B+树只在叶子节点存放数据，同一层的索引节点相比于B树能存放更多索引数据，进一步降低树的高度，而且完整数据只存放在叶子节点，检索效率更稳定，叶子节点之间通过链表维护，顺序查询和范围查询性能更好
劣势 不适合范围查询和顺序查询 极端情况下检索复杂度降低到O(n)，不适合范围查询和顺序查询 需要额外的资源维护树的平衡，同时不适合范围查询和顺序查询 虽然维护成本低，但牺牲了性能，也不适合范围查询和顺序查询 不适合范围查询和顺序查询，查询效率不稳定，存在页合并和分裂 数据冗余度过高，存在页合并和页分裂
适用场景 适用于单行数据查询 尽量别考虑 适用于追求高稳定性，能容忍性能损失 追求高性能和一定程度的稳定性 适合追求高效率，但不存在顺序查询和范围查询的场景 适合高效率场景，并且对顺序查询和范围查询有要求

索引类型

主键索引

InnoDB的主键索引是聚簇索引，数据文件和索引文件是同一个，也就是.ibd文件。InnoDB的数据文件是根据主键组织，如果用户没有指定主键，InnoDB 会自动先检查表中是否有唯一索引且不允许存在 null 值的字段。如果没有这样的字段，InnoDB 将会自动创建一个 6Byte 的隐藏字段作为自增主键。

聚簇索引 & 非聚簇索引

聚簇索引的索引文件和数据文件合二为一，查询速度非常的快，不需要回表。但是更新代价比较大，因为索引文件保存了完整的数据。
非聚簇索引是先通过索引文件定位数据地址，再去访问数据地址，所以存在一次回表查询的操作。但是更新代价会比较小，因为更新数据不会涉及索引文件的修改。

非聚簇索引并不一定会回表查询，如果查询的是主键本身，就不需要回表

覆盖索引

InnoDB只有主键索引是聚簇索引，二级索引（唯一索引、普通索引等）都是非聚簇索引。为了避免频繁回表查询带来的性能问题，引入了覆盖索引，覆盖索引是对于频繁查询的字段，直接将字段的存储在二级索引节点中，而不只是存储主键ID。

覆盖索引

联合索引

使用表中的多个字段创建索引，就是 联合索引，也叫 组合索引 或 复合索引。区别于索引合并，索引合并是多个单列索引分别查询数据，然后合并。联合索引只需要一次检索，索引合并需要多次检索+一次数据合并。

联合索引的查询需要满足最左前缀匹配原则，MySQL 会根据索引中的字段顺序，从左到右依次匹配查询条件中的字段。在使用联合索引时，可以将区分度高的字段放在最左边，这也可以过滤更多数据。

索引下推

EXPLAIN中的extra字段为Using index condition表示使用了索引下推。索引下推出现之前，存储引擎只负责检索数据，至于数据是否符合where子句的条件，是由Server层来判断的。索引下推是指允许Server层执行where子句的部分判断逻辑。

  • 没有索引下推之前，即使 zipcode 字段利用索引可以帮助我们快速定位到 zipcode = ‘431200’ 的用户ID，对每一个找到的用户ID进行回表操作查询完整数据，获取完整的用户数据，再去判断 MONTH(birthdate) = 3。
  • 有了索引下推之后，存储引擎会在使用 zipcode 字段索引查找 zipcode = ‘431200’ 的用户时，同时判断 MONTH(birthdate) = 3。这样，只有同时满足条件的记录才会被返回，减少了回表次数

索引下推既可以解决回表次数，也可以解决Server层与存储引擎之间的数据传输量。

索引下推是跨存储引擎的，InnoDB与MyISAM都支持索引下推

索引下推的应用范围：

  1. 适用于InnoDB和MyISAM引擎
  2. 适用于二级索引，因为本身是为了减少回表次数
  3. 不适用于子查询，子查询建立的临时表不存在索引

索引建立建议

  1. 区分度高的建立索引
  2. 频繁查询的字段建立索引
  3. 用于连表JOIN的字段
  4. 需要排序的字段

被频繁更新的字段尽量不要建立索引，索引底层是按照索引字段的顺序组织的，如果频繁更新，索引文件本身的维护需要很大的成本

为什么建议主键ID索引自增，主键ID自增的话，插入数据只会在最后一个叶节点的末尾插入，不会涉及页的频繁合并和分裂。

单张表上的索引数量不要太多，因为优化器需要选择最优的索引，优化需要时间成本

尽可能建立联合索引而不是单列索引，索引合并会导致多次扫描+一次数据合并

索引失效场景

  1. 查询命中的数据量过多时会导致索引失效，这是优化器优化的原因，认为全表扫描比索引扫描+回表效率更高
  2. 联合索引不满足最左前缀匹配
  3. AND 或 OR操作前后至少有一个不是索引字段
  4. 索引列上有计算或函数操作
  5. 子查询建立的临时表不存在索引

Buffer Pool

MySQL 的数据是存储在磁盘里的，但是不能每次都从磁盘里面读取数据，这样性能是极差的。因此,InnoDB在内存中开辟了一个缓存Buffer Pool，根据局部性原理存储数据页

Buffer Pool存在预读失效和缓存污染问题，Linux也存在这个问题，Buffer Pool是通过将LRU链表拆分为young区和old区来解决这两个问题的。

补充一点，既然有了Buffer Pool，为什么还需要Redis这类中间缓存呢？

  1. Buffer Pool本身是基于关系型模型存储的，检索的时间复杂度依然为O(logn)
  2. 灵活性差，Buffer Pool根据LRU淘汰页面，而Redis可以根据需要动态设置过期时长
  3. Redis的内存管理机制更完善，比如过期机制、内存整理等，Buffer Pool不具备
  4. Redis支持横向扩展集群部署，Buffer Pool不支持

MySQL自增锁

当多个事务同时向带有AUTO_INCREMENT字段的表插入数据时，必须确保每个事务获取到的自增值是唯一的，需要通过锁控制并发问题。
MySQL有三种不同的自增锁模式

  • 传统模式：所有事务在插入语句执行过程中会持有一个表级锁AUTO-INC锁，直到语句执行完才会释放，并发性能比较差
  • 连续模式：对于简单的批量插入语句，InnoDB 会预先计算所需自增值数量，只会在分配自增值时通过一个轻量锁控制并发，分配完自增值立即释放；但是对于无法计算需要的自增值数量的语句，还是需要表级锁控制并发分配
  • 交叉模式：无论是否可以计算所需的自增值数量，都通过轻量锁进行分配，每次分配批量值，如果本次分配的数量不够，会再次进行分配

在交叉模式下，如果binlog的日志格式为statement或者mixed模式，会导致主从数据不一致，因为从节点执行时，执行的顺序或单次分配的数量不同都会导致主从数据不一致

自增锁（AUTO-INC Lock）及其不同模式是InnoDB特有的，因为只有InnoDB支持事务

OLTP

MySQL的InnoDB存储引擎是目前最主流、功能最完善的事务型存储引擎，广泛用于OLTP场景

OLTP(Online Transaction Processing，在线事务处理) 是一种面向事务型应用的数据库设计和处理模式。核心目标是高效、可靠、并发地处理大量短小的事务操作。

特性 说明
事务短小 每个操作通常只涉及少量数据（如插入一条订单、更新用户余额）
高并发 系统需同时支持成千上万用户并发访问（如电商秒杀、银行转账）
强一致性 必须保证 ACID（原子性、一致性、隔离性、持久性）
实时响应 响应时间通常在毫秒级（<100ms）
读写混合 既有查询（SELECT），也有频繁的 INSERT、UPDATE、DELETE
数据量中等 单表通常在 GB 到 TB 级别，但强调“热数据”快速访问

OLTP关注的核心是高效、可靠；而且InnoDB的高可靠是有代价的：锁+MVCC+各种配置协作才能实现高可靠

InnoDB虽然现在被广泛用于OLTP场景，但在某些场景下依然存在很大的限制：

  • 写入新能在高并发下的瓶颈(加锁、undo log膨胀、热点行问题)，QPS在达到一定上限后难以线性扩展
  • 不支持分布式横向扩展
  • 存储空间占用很高(各种持久化日志、B+树底层索引、按整页存储等机制)
  • 按行存储数据，OLAP场景效率很低
