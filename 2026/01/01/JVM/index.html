JVM

概念

JVM也就是Java虚拟机，.java文件被编译为.class文件后，会被JVM解释运行，所以JVM才是java代码运行的容器。Java能够实现内存的自动管理，全仰仗JVM的能力。

自动内存管理

内存区域

JVM在运行时会将管理的内存划分为若干部分，不同的版本有不同的划分方式，JDK1.7和JDK1.8如下：

JDK1.7 JDK1.8

内存区域主要分为两类：

  • 线程私有区域：程序计数器、虚拟机栈、本地方法栈
  • 线程共有区域：堆、方法区、本地内存

其中本地内存不属于运行时数据区域，是独立于JVM内存之外的

对于进程来说，可共享的资源很少，比如内核资源、系统级共享资源（CPU、网络资源、文件与I/O资源、共享内存）

程序计数器

程序计数器用于存储当前线程的下一条指令在内存中的地址，为了在线程调度前后，每个线程都能正确恢复到自己上次执行的位置，程序计数器是线程私有的。

程序计数器是唯一一个不会出现OOM的区域，随着线程创建而创建，随着线程消亡而消亡

栈

方法的执行伴随着入栈，结束伴随着出栈，每个线程都有自己的执行逻辑，为了避免线程之间的任务相互打扰，栈空间也是私有的。栈分为虚拟机栈和本地方法栈，区别在于执行的是Java方法还是本地方法。生命周期随着方法的执行而创建，随着方法的结束而死亡。

栈帧一般包含局部变量表、操作数栈以及方法返回地址等元数据信息

栈的空间是有限的，当线程请求栈的深度超过当前 Java 虚拟机栈的最大深度的时候，会抛出StackOverflowError，如果栈的内存大小可以动态扩展， 那么当虚拟机在动态扩展栈时无法申请到足够的内存空间，会抛出OOMError。

无论是正常返回还是抛出异常，栈帧都会被弹出，正常返回和抛出异常都算作方法结束

堆

Java 堆是所有线程共享的一块内存区域，在虚拟机启动时创建。此内存区域的唯一目的就是存放对象实例，几乎所有的对象实例以及数组都在这里分配内存。

堆空间结构

在JDK1.7及之前，堆空间被划分为新生代、老年代和永久代，其中永久代是方法区的物理实现，用于存储Class、即时编译机器码等，在JDK1.8中被元空间取代，元空间位于本地内存。堆空间最易出现的也是最频繁出现的就是OOMError。

这里简答对比一下栈空间和堆空间的区别：

维度 堆空间 栈空间
生命周期 与JVM进程保持机制 与线程保持一致
存储元素 主要为引用数据类型 可存储基本数据类型和引用数据类型
用途 用于对象的实例分配 用于方法的执行

字符串常量池是JVM为了避免字符串的频繁创建而开辟的一段缓冲区。字符串常量池位于堆中，因为该常量池的垃圾收集频率也很高

方法区

方法区属于是 JVM 运行时数据区域的一块逻辑区域，是各个线程共享的内存区域，JDK的每个版本都有不同的方法区实现。在JDK1.7中具体的实现是永久代，但后续版本被元空间取代。

方法区存储的数据主要为：类的元数据（Class对象）、静态变量以及Code Cache（JIT编译生成的代码）等。

为什么要使用元空间替换永久代呢？

  • 永久代位于堆中，大小受堆内存的限制，而元空间位于本地内存，更大的空间可以加载更多的类
  • 永久代本身的垃圾收集效率很低，和新生代老年代的收集频率差异很大，位于堆中会为GC带来不必要的复杂度

区别于字符串常量池，运行时常量池位于方法区中，每一个接口或类在被编译为为.class文件后都会维护一个静态常量池，用于存储编译期间的字面量或者常量，在被JVM加载读取后，成为运行时常量池。

对象创建过程(new指令执行过程)

  1. 虚拟机遇到一条new指令时，会先检查该类的Class是否被加载过，也就是元空间是否存在Class对象，如果不存在，执行相应的类加载过程
  2. 内存分配，内存分配有两种方式：CAS失败重试或TLAB方式
    • CAS失败重试：并发分配内存时，通过CAS失败重试（高并发下，失败概率高）
    • TLAB：为每一个线程在Eden区预先分配一块内存，JVM 在给线程中的对象分配内存时，首先在 TLAB 分配，当对象大于 TLAB 中的剩余内存或 TLAB 的内存已用尽时，再采用上述的 CAS 进行内存分配
  3. 设置对象头，比如Class对象指针、分代年龄等
  4. 执行构造方法

类加载过程

类加载过程分为三个阶段：加载、连接以及初始化。类加载过程本质上就是将.class文件代表的字节码静态数据结构转化为运行时数据结构Class对象，供运行时访问。类加载过程的核心组件是类加载器，负责静态到动态的转化。

加载

类加载器是一个负责加载类的对象，每一个类都有对应的ClassLoader负责该类的加载过程。类加载器基于双亲委派模型进行加载，具体流程如下：

  1. 在类加载的时候，系统会首先判断当前类是否被加载过。已经被加载的类会直接返回，否则才会尝试加载（每个父类加载器都会走一遍这个流程）。
  2. 类加载器在进行类加载的时候，它首先不会自己去尝试加载这个类，而是把这个请求委派给父类加载器去完成（loadClass方法）
  3. 只有当父加载器反馈自己无法完成这个加载请求（它的搜索范围中没有找到所需的类）时，子加载器才会尝试自己去加载（调用自己的 findClass() 方法来加载类）
  4. 如果子类加载器也无法加载这个类，那么它会抛出一个 ClassNotFoundException 异常

JVM判断两个类是否相同的规则：不仅要看全限定类名是否相同，还要看类加载器是否相同

那这种双亲委派模型有什么好处呢？

  • 避免类的重复加载：即使定义了同名的核心类，双亲委派模型确保核心类总是由BootstrapClassLoader 加载，保证了核心类的唯一性
  • 安全性：对于java.开头的类，会在加载时进行安全检查，阻止恶意代码定义

双亲加载机制保证了加载过程的唯一性和安全性，然而在某些特殊情况下，需要打破双亲加载机制，让子类加载器优先加载某些类，而不是先委托给父类加载。

为了保证安全，父加载器无法加载子类加载器的类，如果BootStrapClassLoader可以加载子类加载器的类，那JVM直接就被用户劫持，随意更改了。

**那什么时候需要打破双亲加载机制呢？**最经典的一个场景，SPI机制，接口由JDK提供，并且由BootStrapClassLoader加载，比如JDBC，Driver在JDK中有接口，但具体的实现可以由用户去任意实现，遵循接口规则即可，上层父类加载器无法加载用户实现的Driver，JDBC使用了线程上下文类加载器，能够看见项目里所有的类，直接绕过了双亲加载机制。打破双亲加载的本质是用灵活性换安全性

连接

连接阶段负责验证Class对象字节流是否符合当前JVM要求，保证不会危害虚拟机安全，此阶段还会为变量分配设置默认初始值

初始化

执行类构造器 init方法，完成类变量的真正初始化

垃圾回收机制

内存分配回收原则

  1. 对象优先在Eden区分配
  2. 大对象直接进入老年代，大对象占用大量的内存空间，减少新生代垃圾回收的频率
  3. 长期存活的对象（大于15岁）进入老年代
  4. 空间分配担保机制：在Minor GC前，判断老年代的连续空间是否大于新生代对象总大小或者历次晋升的平均大小，就会进行 Minor GC，否则将进行 Full GC

Minor GC只回收新生代的垃圾，而Full GC则回收整个堆+方法区的垃圾

触发Minor GC的场景：

  • 新生代空间不足，无法容纳新的对象

触发Full GC的场景：

  • 老年代空间不足（空闲空间无法容纳大对象或晋升的新生代）
  • 元空间不足（加载的类过多）
  • System.gc()手动触发整堆收集
  • 空间分配担保失败

死亡对象判断方法

  • 引用计数法：每个对象分配一个引用计数器，表示当前引用该对象的数量，为0表示可回收，但是存在循环引用问题
  • 可达性分析算法：以GC ROOT为起点遍历对象引用链并进行标记，遍历完之后没有被标记的则为垃圾

GC Root不是对象，而是对象的引用，所以即使对象没有初始化，其引用是确定的。虚拟机栈中的局部变量、方法区静态变量、方法区中常量引用的对象、所有被同步锁持有的对象等可以作为GC root

之前说过，方法区也是垃圾收集的区域，那方法区主要收集的是哪些垃圾呢？答案是类，也就是Class，如何判断无用类呢？

  • 该类的所有实例已被回收
  • 该类的类加载器已被回收
  • 该类没有在任何地方被引用

垃圾回收算法

维度 标记-清除算法 标记整理算法 复制算法
适用区域 老年代 老年代 新生代
优势 基本没优点 无内存碎片，内存利用率高 高效，复制成本很低
劣势 标记和清除过程的效率不高，存在内存碎片 标记整理过程效率不高，适合老年代这种收集频率不高的 可用内存只有原始的一半

目前广泛采用分代收集算法，这也是为什么将整个堆划分成不同区域的原因。每个年代适合不同的收集算法，比如新生代，死亡的频率很高，适合用复制算法，存活率低，复制效率很高，而对于老年代，对象的存活率很高，更适合适用标记整理算法，分代收集可以针对每个年代的特点选择最合适的收集算法。

垃圾回收的大对象回收问题

在 JVM 中，大对象通常指大小超过某个阈值的对象，默认情况下，对象首先在Eden区分配，但由于大对象占用空间较大，会导致新生代空间被迅速消耗导致频繁minor GC。

大对象问题的定位

  • 查看GC日志，如果GC频率很高，并且回收的内存很少的话，可能出现了大对象问题
  • 使用MAT工具分析内存快照，还可以使用Histogram视图查看对象的实例数量和内存占用情况

如何优化大对象问题

  • 增大堆内存空间(-Xmx、-Xms)
  • 调整新生代和老年代的空间比例
  • 使用对象池，避免大对象的重复创建，提高对象的复用率
  • 使用软引用或弱引用，内存不足时回收对象

Stop The World （STW）

STW是垃圾回收中的一个概念，也就是垃圾回收器工作期间，不允许业务线程并发，需要阻塞垃圾回收之外的所有操作，是早期垃圾回收为了保证 GC 过程中堆内存状态的一致性而采用的措施。STW实现的核心机制是安全点+线程挂起。

安全点是线程执行期间的一些特定位置，在安全点，所有对象的引用状态是明确的，比如线程中的对象引用关系都已同步到内存，GC可以安全地进行垃圾回收，常见的安全点包括方法return或抛出异常。当GC需要STW进行垃圾回收时，会设置一个全局标志，所有的业务线程在到达每一个安全点时定期检查这个标志，如果发现标志被垃圾回收器重置，则在当前安全点将线程挂起。当所有线程进入安全点挂起后，GC开始执行垃圾回收，垃圾回收完之后，清除STW全局标记，唤醒所有阻塞线程。

JDK GC的垃圾回收属于协作式调度

垃圾收集器

  • Serial收集器：单线程收集器，垃圾收集期间STW
  • ParNew收集器：Serial收集器的多线程版本，依然是STW收集器
  • Serial Old收集器：Serial收集器的老年代版本
  • Parallel Old收集器：ParNew收集器的老年代版本
  • Parallel Scavenge收集器：在ParNew收集器的基础上，提供了大量参数供用户找到最大吞吐量，也配备了自适应调节策略，把优化交给虚拟机完成
  • CMS收集器：第一款真正意义上的并发收集器，以获取最短回收停顿时间为目标的收集器，基于标记-清除算法
  • G1收集器：面向服务器的垃圾收集器，以建立可预测的停顿时间的垃圾回收为目标
  • ZGC收集器：JDK21的默认收集器

JDK8的默认垃圾收集器:新生代Parallel Scavenge+老年代Parallel Old收集器；JDK9的默认垃圾收集器是G1

接下来对三款并发收集器做详细介绍：

CMS收集器

CMS收集器的工作过程总体上可以分为四个过程：

  1. 初始标记：标记与GC ROOT直接相邻的对象，短暂停顿
  2. 并发标记：同时开启GC和业务线程，因为对象的可达性在并发过程中会发生变化，所以会跟踪记录标记完成后，引用更新发生变化的地方
  3. 重新标记：修正并发标记期间引用更新的地方，停顿时间较长
  4. 并发清除：开启用户线程，同时 GC 线程开始对未标记的对象做清扫
CMS收集器工作过程

在并发标记阶段提到，会跟踪记录引用发生更新的地方，此处采用的是增量更新+插入式写屏障技术，即当已被扫描的引用发生更新时，加入重新扫描队列，重新对其扫描，保证不会被误回收

CMS收集器在初始标记和重新标记阶段是STW的，由于是第一款并发收集器，因此存在很多缺陷：

  • CPU资源敏感：业务线程和GC线程抢占CPU
  • 标记清除算法存在大量内存碎片
  • 浮动垃圾，在并发清除阶段会产生新的垃圾，这部分浮动垃圾只能等到下次垃圾回收才能被标记；并且并发回收期间的增量更新+插入式写屏障也会导致垃圾未被标记（一个非垃圾对象转化为垃圾对象）

G1收集器

G1 摒弃了传统 GC “固定分代物理边界” 的设计，将整个堆内存划分为多个大小相等的独立 Region，属于分区收集算法，但保留了分代的概念，即一个Region属于新生代Region或老年代Region。此外，为了存放大对象（大小≥Region 大小的 50%），专门开辟了大对象Region。

工作流程如下：

  1. 初始标记： 标记从 GC Roots 可直接引用的对象，即标记所有直接可达的活跃对象
  2. 并发标记：与应用并发运行，标记所有可达对象。 这一阶段可能持续较长时间，取决于堆的大小和对象的数量。
  3. 最终标记： 短暂停顿（STW），处理并发标记阶段结束后残留的少量未处理的引用变更。
  4. 筛选回收：根据标记结果，选择回收价值高的区域，复制存活对象到新区域，回收旧区域内存。这一阶段包含一个或多个停顿（STW），具体取决于回收的复杂度。
G1收集器工作过程

并发标记期间，通过原始快照+混合屏障来跟踪引用发生更新的对象，避免漏标。通过卡表+记忆集解决跨代引用问题。

ZGC收集器

G1 的 STW 时间会随堆内存增大而线性增加，而 ZGC 的 STW 时间几乎与堆大小无关，全流程并发，不存在STW阶段，是一款低延迟、可扩展的垃圾回收器‌，专为‌超大堆内存（TB级）‌场景设计。

ZGC的全流程并发基于染色指针+读屏障实现。在 64 位 Linux 系统中，对象指针的高 18 位闲置未用于寻址，剩余 46 位原本可支持 64TB 内存寻址。ZGC 从中提取高 4 位作为标志位存储对象状态，剩余 42 位仍能支持 4TB 内存寻址，这也是 ZGC 最大支持 4TB 内存的原因。标志位用于存储对象的染色标记(黑、灰、白)。ZGC 通过读屏障+内存映射技术，将标志位不同，但低42位相同的地址对应的不同虚拟内存地址映射到同一物理内存地址，以此解决指针标记位变动时的寻址问题，延迟非常非常低。

跨代引用

跨代引用是指在内存区域中，一个分代的对象引用了另一个分代的对象，若处理不当，会导致 GC 漏标存活对象。分代GC的优势是按需回收某一代，不需要全堆收集，但跨代引用打破了这个优势。假如当前正在执行Minor GC回收新生代，一个新生代对象没有被新生代的其他对象引用，而是被一个老年代对象引用，如果不解决跨代引用，就会漏标这个对象。

那怎么办才能既避免全堆收集，又能解决跨代引用呢？答案是空间换时间，用卡表+ 记忆集的空间换全堆收集的时间。

具体来说，将整个堆内存划分为多个大小固定的 “卡页（Card Page）”（默认 512 字节），每个卡页对应卡表中的一个 “标记位（Card Entry）”—— 卡表本质是一个字节数组，数组下标对应卡页的内存地址，数组值表示该卡页的状态（如 “脏卡”）。当老年代对象引用新生代对象时，JVM 会通过写屏障将对应的卡表项设置为脏卡。在Minor GC扫描时，无需整堆扫描，只需扫描老年代对应的脏卡对象。

G1中引入了记忆集，用于记录跨代Region的引用，记忆集从一个全局的数据结构转化为Region级别的数据结构，记忆集相当于一个哈希结构存储了引用来源Region的地址和目标Region的地址。

比如 “老年代 Region S 的对象引用新生代 Region T 的对象”（老年代→新生代跨代引用）：卡表标记 S 中该引用所在的卡页为脏卡；T 的 RSet 会记录 “S + 该脏卡页”；当回收 T（新生代 Region）时，无需扫描整个老年代，只需遍历 T 的 RSet，找到 S 中的脏卡页，扫描这些卡页即可 —— 实现了 “跨代引用的精准定位”。

三色标记算法

三色标记算法是并发垃圾收集器的核心标记算法，通过给对象标记 “白、灰、黑” 三种颜色，跟踪对象的可达性状态，解决GC与业务线程并发时准确标记可达性对象的问题。

颜色 核心含义 状态转换条件
白色 未被 GC 线程访问过（默认状态）；若标记结束后仍为白色，视为垃圾对象 初始时所有对象均为白色；被 GC 线程扫描到（发现可达）后，转为灰色
灰色 自身已被 GC 线程标记，但引用的子对象（如成员变量指向的对象）尚未扫描 自身标记完成后，GC 线程开始扫描其引用的子对象；所有子对象扫描完成后，转为黑色
黑色 自身及所有直接 / 间接引用的子对象均已扫描完成，确认是存活对象 灰色对象的所有子对象均被标记（转为灰 / 黑色）后，自身转为黑色；标记结束后保持黑色

从整个流转过程可知：

  • 黑色对象不允许指向白色对象，因为黑色对象表示自己以及自己的子对象全部扫描完成，不会再次扫描，导致非垃圾对象被当成垃圾回收
  • 白色对象失去本次被标记的机会

如果出现了满足以上两种情况的场景，就会出现错标问题，导致非垃圾对象被标记为垃圾对象。

标记过程结束后，对象非黑即白

写屏障技术

在并发标记期间，收集器采用三色标记算法对引用链上的对象进行标记，如果GC线程已扫描的引用被业务线程更改，就会导致错标、漏标问题，怎么解决呢？出现漏标需要满足两个条件：

  • 黑色对象指向白色对象
  • 白色对象失去了本次GC标记机会（断开与灰色或白色对象的引用关系）

只要破坏以上任意一个条件，就可以解决漏标问题。

  • 增量更新：破坏第一个条件，当一个黑色对象指向白色对象时，通过插入式写屏障技术记录这个引用变更，重新标记阶段重新扫描这些发生变更的黑色对象，避免错标
  • 原始快照： 破坏第二个条件，在并发标记开始之前，生成一张原始快照，当白色对象脱离灰色对象的引用时，通过删除式写屏障技术记录这个引用变更，记录灰色对象，在重新标记阶段，重新扫描原始快照中对应的灰色对象，给予白色对象二次扫描的机会
维度 增量更新 原始快照
跟踪目标 盯紧「新增引用」（黑色→白色） 盯紧「删除引用」（任意→白色）
核心动作 把黑色对象打回灰色，重新扫描其所有引用 记录被删除的引用，按「初始快照」标记白色对象为存活
写屏障触发时机 引用赋值时（obj.field = newRef） 引用删除时（obj.field = null）
关键取舍 减少浮动垃圾，但重复扫描大量对象 允许更多浮动垃圾，但扫描范围更精准
典型实现 CMS、ZGC G1

增量更新不适用于分区收集算法，以G1为例，G1并不回收所有垃圾，而是筛选回收价值大的区域进行回收，举个例子：

  1. G1 本次只想回收 3 个 Eden Region（部分收集）；
  2. 并发标记阶段，一个老年代的黑色对象 A（属于非收集 Region）新增了指向 Eden Region 白色对象 B 的引用；
  3. 按增量更新，A 会被打回灰色，GC 必须重新扫描 A 的所有引用（可能指向 1000 个其他老年代对象）；
  4. 原本只需扫描 3 个 Eden Region，结果被迫扫描老年代的 A 对象及其所有引用，STW 时间大幅超标

采用原始快照可以实现精准扫描，GC 只需处理 “被删除的引用”，这些引用直接指向白色对象，无需遍历其他无关引用

G1是如何计算每个Region的回收价值并选择回收价值高的回收呢？核心计算公式：回收价值 = 可释放内存 / 预估回收耗时，根据公式获得每个Region的优先级，按回收价值从高到低排序所有 Region（如果回收价值相同，优先回收Eden Region）
