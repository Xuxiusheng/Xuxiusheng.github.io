Redis基本数据类型

Redis 共有 5 种基本数据类型：String（字符串）、List（列表）、Set（集合）、Hash（散列）、Zset（有序集合），底层结构如下所示：

String List Hash Set Zset
SDS LinkedList / ZipList / QuickList Dict / ZipList Dict / Intset ZipList / SkipList

需要注意的是，虽然底层数据结构会自动演变，但是只有升级过程，没有降级过程

String

Redis的作者基于C语言构建了一种简单动态字符串(SDS)，将其作为Redis基本字符串类型，相比于C语言原生字符串，有如下优势：

  • O(1)时间复杂度获取字符串长度，SDS增加了len字段记录当前字符串的长度
  • 二进制安全，C语言以\0作为字符串结尾标识，在一些二进制文件，视频、音频等文件中存在\0字符，会导致解析错误，SDS通过len判断字符串结束位置，不存在这个问题
  • 空间预分配策略，在申请空间时，会根据特定的算法获取额外的空间，避免频繁的空间分配
  • 避免缓冲区溢出，通过free字段判断当前剩余空间是否满足要求，避免直接拼接导致的缓冲区溢出

String类型是缓存中最常用的类型，适用于简单的KV存储、计数器以及会话信息存储等功能

List

Redis常用的一个基本数据类型就是List，其底层有linkedlist、ziplist、quicklist三种底层实现

LinkedList

LinkedList很简单，就是单纯的双向链表，Redis本身是一个KV键值数据库，LinkedList却要消耗额外的两倍内存保存前后指针，因此内存浪费很严重，因此出现后续的ZipList

ZipList

从ziplist可以看出，其内存空间是连续的，因此不需要前后指针记录前驱和后继节点位置，而且不存在外部内存碎片，entries为一个连续数组，负责存储实际的元素，数据结构如下

级联更新问题

ZipList的存储效率很高，但是操作效率在元素数量很大的情况下会严重下滑。每一个entry占用的空间长度不同，所以需要从头或尾进行遍历，如果是增删改操作，还涉及到级联更新问题。

前面提到，entry中有一个prelen字段，它的长度要么是1个字节，要么都是5个字节：

  • 前一个节点长度小于等于254，则prelen为1个字节
  • 前一个节点长度大于254，则prelen为5个字节

假如，已有的节点长度都在250-254之间，此时插入一个长度为255的entry到头部，此时，第二个节点的prelen需要转化为5个字节，导致第二个entry节点大于254，需要继续更新第三个节点，一直到最后一个节点，这就是级联更新问题，存储节点的压力会非常大

总之，综合操作效率和级联更新带来的问题，ziplist只适合在元素数量较小的情况下采用

QuickList

既然ZipList在元素数量较小的情况下存取效率很高，那有没有什么办法既能保留ZipList已有的优势，又能解决在大数据量下的劣势呢？有！！！！QuickList！！！！

可以看出，quicklist相当于结合了linkedlist和ziplist，每个节点的ziplist只保存少量元素，同时quicklistNode节点的数目又能很少，内存浪费比例很低，当前默认的List采用quicklist结构

Set

Set集合用于存储唯一元素，底层支持两种数据结构

  • intset：当集合元素均为整数且个数小于512，默认使用intset，节省内存空间
  • hashtable：当存储元素不满足intset的要求时，会转化为hashtable

Set支持集合的交集、并集和差集操作，可以用于抽奖系统

Hash

Hash支持两种底层结构：

  • ziplist：当元素个数小于512且元素大小小于64字节
  • hashtable：不满足ziplist的要求，转化为hashtable

在元素数量较小的时候，ziplist的内存紧凑，存取效率很高，当元素数量上涨时，由于需要遍历，性能下降，采用hashtable，存取时间复杂度为O(1)

扩容 & 缩容

Redis的扩缩容规则与Java的Map不同，具体规则如下：

  • 当前Redis正在执行BGSAVE或BGREWRITEAOF，负载因子大于等于5时执行扩容，扩至原来两倍
  • 当前Redis未执行BGSAVE或BGREWRITEAOF，负载因子大于等于1时执行扩容，扩至原来两倍
  • 负载因子小于等于0.1时执行缩容，缩至大于等于当前元素个数的2的n次幂

之所以需要区分是否正在执行BGSAVE或BGREWRITEAOF，是因为在这两个命令期间，内存的占用率会很高，为了避免进一步加重内存负担，所以等到负载因子大一些再进行扩容/缩容

渐进式rehash

Redis的rehash比较特殊，采用的是渐进式rehash，即并不是一次性迁移全部数据，而是分批多次迁移。在客户端命令命中该hash表时，进行部分数据的迁移，分担一次性迁移的压力，属于分而治之的思想。

  • rehash期间节点可以正常响应外部命令，增命令只需要操作新的hash表，删改查均需要先操作旧表，再操作新表
  • 定时器定时扫描未完成迁移的hash，之前也说了，渐进式迁移的前提是客户端命令可以命中hashtable，但是如果没有命令命中，那是不是迁移永远无法完成呢？当然不是，有一个服务器定时命令定时扫描未完成迁移的hash，并进行迁移。

ZSET

参考ZSET

ZSET是一个比较特殊的结构，元素带有权重，并且内部按照权重排序，属于有序集合，可以用于排行榜等应用。支持两种底层数据结构：

  • ziplist：元素个数小于128，且元素大小小于64字节
  • skiplist：不满足ziplist的要求

实际上，当使用跳表为底层结构时，底层还有一个hash，用于存储key到score的映射，而skiplist存储的是score到key的映射
