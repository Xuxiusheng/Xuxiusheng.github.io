传输层协议

协议

TCP协议

先来简单看下TCP协议的协议格式

TCP协议格式

这里先简单介绍下各个字段的作用：

  • 源端口和目标端口：与网络层的IP一起用于确认端到端连接
  • 序列号、确认应答号：用于保证网络包的乱序和丢包问题
  • 首部长度：TCP协议头为变长头部
  • 窗口大小：用于实现拥塞和流量控制
  • 控制位：用于标识当前数据包的类型

TCP协议头不包含IP地址，协议栈是一个分层模型，IP地址字段位于IP协议头中

为什么端口号不放在网络层或者IP地址不放在传输层呢？
遵循单一职责原则，网络层只负责端对端的通信，至于数据包来源于主机上的哪个应用程序，网络层并不关心，只负责传输和收发数据包，由传输层标识数据包具体的来源（端口号标识）。端口号的作用就是用来区分同一台主机上的不同应用程序或服务

TCP协议工作在传输层，既然IP网络层负责传输，那传输层有什么用呢？IP层不保证网络包可靠交付，只负责传输。打个比方，你找了个导游，但是这个导游不专业脾气也不好，那你怎么投诉或者去找售后呢？那就是这个导游所在公司的售后部门，传输层相当于是给网络层“擦屁股”。

TCP连接是一个抽象的概念，那体现在具体的实现中是什么呢？答案是两台主机上的Socket和维护这条连接的元数据。TCP连接在物理上是不存在的，简单来说的话就是两台主机在状态信息上达成一致，并分配Socket来处理数据流。

TCP协议的三大特性：

  • 面向连接：TCP协议只支持一对一通信，通信双方必须建立连接
  • 可靠：无论网络发生何种问题，都能保证数据包可靠交付
  • 基于字节流：非结构化报文，应用层消息会被划分合并，因此需要显式规定消息边界规则

面向连接： 四元组（源IP，源端口，目标IP，目标端口）可唯一确认一条TCP连接，IP字段（32位，IPv4）位于IP协议头，端口字段（16位）位于TCP协议头，所以可以推断出一台使用Ipv4的服务器理论上最多存在2^32 * 2^16条TCP连接，但实际上由于OS 文件描述符、连接队列、内存等资源的限制，连接数的上限远小于这个理论值

可靠传输： TCP协议保证数据包能够到达接收端，且按序重组数据，即使发生丢包，会有相应的重传机制重传丢失的数据包。除此之外，还提供拥塞控制和流量控制

基于字节流： 一个完整的数据包会被分割成多个子数据包，不同消息的子数据包可能会被组装成一个数据包，因此会存在粘包问题

UDP协议

与TCP相对的还有一个UDP协议：

UDP协议

与TCP协议相比，UDP的协议相当简单，只包含端口和包长度信息，协议长度是固定的8字节，而TCP协议首部长度为4，因此最大为16字节，变长。

  • 无连接：不需要事先进行三次握手建立连接
  • 尽最大努力传输：能发多少发多少
  • 一个UDP报文就是一个完整的数据包

无连接： UDP协议不需要建立连接，只要数据到来，立刻发送，即不需要提前同步状态信息
尽最大努力传输： 不提供流量控制、拥塞控制和重传等功能，即不保证可靠传输，能发多少是多少，数据丢了也不管
面向报文： UDP协议报文就是完整的数据包

TCP和UDP协议的根本区别在于数据发出去之后怎么办？

  • TCP协议保证数据可达，提供售后
  • UDP协议直接什么都不管了，不提供售后

两种协议的应用场景

TCP协议： 适用于对数据准确性和完整性要求高的场景，比如电子邮件、文件传输等场景，可靠性优先级最高
UDP协议： 能容忍数据一定程度的丢失，速度和低延迟是首要任务的场景，比如视频、游戏等场景。这类实时场景如果丢包重传会导致后续所有数据卡住，不能使用TCP

TCP 和 UDP 可以使用同一个端口吗

端口只是为了区分应用程序，而不是为了区分协议本身。现代的应用程序会根据不同的场景选择不同的协议，因此同一个端口，可以同时存在两种不同的协议。比如一个游戏应用，登录模块采用TCP协议，而游戏内（语音、战斗等）模块采用UDP协议。

TCP三次握手

TCP三次握手
  1. 客户端初始化随机序列号，并填充到SYN报文的序列号字段，发送SYN报文，进入SYN_SENT状态
  2. 服务端接收SYN报文，并且服务端也会发送一个SYN报文给客户端，并且回复客户端ACK，进入SYN_RECV状态
  3. 客户端接收服务端的SYN+ACK报文，回复ACK，进入ESTABLISHED状态
  4. 服务端收到ACK，进入ESTABLISHED状态

SYN报文的序列化是随机初始化的：

  • 避免旧连接的数据包混淆，假如客户端与服务端建立连接后发送一个数据包，此时客户端宕机重启，重新建立连接，假如之前发送的数据包由于网络阻塞在二次建立后才到达服务端，就会导致数据混乱。随机数是会基于时钟计时器递增的，基本不可能会随机成一样的初始化序列号

SYN报文丢失重传时，序列号是相同的，不会重新随机初始化，以此来标识是同一个连接的SYN报文

SYN Flood洪水攻击

服务端在接收TCP连接时，会创建半连接对象存储在SYN队列，完成连接的会创建连接对象存储在accept队列，两个队列大小有限，超过这个大小后，后续的连接请求会被丢弃。SYN Flood攻击就是伪造大量的SYN报文将半连接队列打满，从而导致正常的客户端无法建立请求，那如何应对呢？

  • 减少SYN+ACK报文的重传次数，加快处于SYN_RECV状态的连接断开
  • 开启tcp_syncookies机制，通过cookie绕过半连接队列建立连接

既然cookie方式这么安全，为什么不全部使用呢？
服务器需要为每个SYN包执行一次密码学哈希计算（通常使用SHA1或MD5）来生成和验证Cookie。虽然单次计算开销不大，但在每秒处理数十万SYN包的高性能服务器上，这个额外的CPU计算负担会显著影响性能，成为瓶颈。

TCP四次挥手

TCP四次挥手

通信双方均可以发起挥手断开连接，这里将发起挥手的主机称为客户端

  1. 客户端计划断开连接，发送FIN报文，客户端进入FIN_WAIT_1状态
  2. 服务端收到FIN报文，立即回复ACK，服务端进入CLOSE_WAIT状态
  3. 客户端收到ACK报文，进入FIN_WAIT_2状态
  4. 服务端数据发送完毕后，发送FIN报文，服务端进入LAST_ACK状态
  5. 客户端收到FIN报文，回复ACK报文，服务端收到ACK报文后，进入CLOSE状态
  6. 客户端发送ACK报文后立即进入TIME_WAIT状态，经过2MSL后，进入CLOSE状态

主动关闭方才有TIME_WAIT状态

可以看到服务端收到FIN之后，立即回复ACK报文，但是因为服务端可能还有数据需要发送，所以不能立即发送FIN报文，等待数据发送完毕再发送FIN报文。如果服务端没有数据需要发送了，第二次和第三次挥手可以合并优化为一次挥手。

FIN报文只表示没有数据需要发送，但是依然可以接收数据

只要是数据报文，就会存在丢失的风险，那如果挥手报文丢失，连接还能正常关闭吗？
答案是可以， 挥手报文丢失会重传，重传之后依旧丢失，客户端会直接清除本机的连接状态信息，以粗暴的形式关闭。

主动方可以通过close和shutdown关闭TCP连接，这两个有什么区别呢？

  • 主动关闭方调用close函数在收到ACK之后进入FIN_WAIT_2之后，持续60s，如果60s未收到第三次挥手，直接粗暴关闭
  • 主动关闭方调用shutdown函数在收到ACK之后进入FIN_WAIT_2之后，只要未收到第三次挥手，就会一直等待，死等

延申一个问题，重启 TCP 服务进程时，为什么会出现“Address in use”的报错信息？又该怎么避免？
关闭TCP服务后，会发起四次挥手，主动发起方在最后会有一个TIME_WAIT状态，持续2MSL（报文最大存活时间），以保证服务端正常关闭。如果在TIME_WAIT还未结束的情况下重启进程，由于资源依然被占用，所以出现该报错信息。

开启SO_REUSEADDR机制，操作系统允许新的服务进程立即绑定到一个尚未完全结束（处于 TIME_WAIT状态）的端口上，从而实现服务的无缝、快速重启
那旧连接的数据包不会被新连接误认吗？不会新旧连接的序列号是随机初始化的，旧连接的数据包会因为序列号不匹配被丢弃

进程崩溃和主机宕机挥手有区别吗？

  • 进程崩溃的情况下，内核会正常完成四次挥手关闭连接
  • 如果是主机宕机，对端发送数据直到重传次数用完之后依旧失败，会强制清除此连接占用的资源，关闭连接

保活机制

TCP 保活机制可以在双方没有数据交互的情况，通过探测报文，来确定对方的 TCP 连接是否存活。

在一个时间段内，如果连接没有数据传输会触发保活机制，保活机制在之后会每隔一段时间发送探测报文，如果连续几个探测报文都没有响应，就会触发连接关闭。

如果已经建立了连接，但是客户端突然出现故障了怎么办？

两个主机建立了TCP长连接，假设没有保活机制的情况下，客户端宕机，如果服务端一直不发送数据，那就一直感知不到客户端的情况，会一直维持着保持连接需要的资源。有了保活机制后，即使没有数据发送，也会定期发送探测消息给对端主机，以此确保正常工作，并在出现异常的情况下，及时释放资源。

经过以上介绍，可以看出TCP协议可以保证可靠传输，那这能说明数据一定不会丢失吗？
当然不能！！ TCP是传输层协议，其上还有应用层，数据在应用层可能发生丢失。

TCP可靠传输

在错综复杂的网络世界，网络数据不可避免地会出现丢包、重复和数据乱序等问题，TCP作为一个保证可靠性的协议，自然提供了解决这些问题的办法。

确认-应答机制

TCP实现可靠传输的方案之一是确认-应答机制，可以解决丢包、重复和乱序等问题。体现在TCP协议头中的话，就是通过序列号和确认应答号两个字段来实现。发送端主机发送数据包，接收端主机收到数据后回复应答消息，告诉发送端数据已收到。

确认-应答机制

当发送端在限定时间内未收到消息或应答号顺序错乱，会触发重传机制。

超时重传

当数据包丢失或应答报文丢失时，会触发超时重传机制

数据报文丢失 应答报文丢失

可以很直接地看出，超时重传的效率和超时时间的设定密切相关。

  • 超时时间过长，重发效率低，过了很久才触发
  • 超时时间过短，很容易导致没有丢包就重发，增加网络阻塞

理论上的最优超时时间应该略大于报文的RTT，也就是往返所需要的时间。在实际的协议栈实现中，超时时间是动态计算的，会根据数据报文的实时RTT和历史RTT计算一个平滑值。

快速重传

超时重传的缺陷是超时周期过长，并且超时时间需要动态计算，那有没有方法能够省去超时等待的时间呢？有，使用快速重传。

快速重传的思想很简单，如果接收端发现报文丢失，就连续回复三个相同的应答报文

快速重传

快速重传解决了超时重传的等待时间过长的问题，但是带来了一个新的问题，以上图为例，假如Seq2和Seq3都丢失，第一次重传，只能重传Seq2，Seq3的重传需要再发送三个相同的应答报文才能重传，效率比较低。

在快速重传的基础上衍生了SACK机制，SACK字段位于TCP协议头的选项字段中，用于存储缺失的数据报文序列号，发送端收到三个相同的应答号后，会解析SACK字段精准重传丢失报文。

SACK重传

SACK机制需要通信双方都支持，因此这个机制需要在握手时进行确认。

超时重传和快速重传一般组合使用，在网络轻微阻塞的情况下，快速重传能够迅速感知到丢包现象，重传效率较高。在网络严重阻塞的情况下，应答报文可能也会阻塞，这时候超时重传开始发挥作用。

滑动窗口

确认-应答机制可以解决数据包的丢包、乱序等问题，可以解决数据包的局部问题。对于更加宏观的概念，比如批量传输、网络阻塞等问题则通过滑动窗口来解决。

批量发送

TCP基于确认-应答机制发送报文，每发送一个数据，都要进行一次确认应答。当上一个数据包收到了应答了，再发送下一个。这种效率相当低，在发送端等待应答的这段期间，什么都做不了，只能傻等。此外，RTT越大，网络吞吐量越低。

为了解决这种通信效率过低的问题，TCP引入了滑动窗口，窗口实际上是操作系统内核维护的一段缓冲区，窗口内的数据无需等待应答，可以直接发送，收到应答报文后，滑动窗口可以向后移动。

累积确认机制：发送端不必一定接收所有的应答报文，只要接收到一个应答报文，该应答号之前的报文一定被接收端接收了，因此窗口可以直接后移，这叫做累积确认。

滑动窗口知道是什么了，那窗口的大小怎么确定呢，如果发送窗口过大，接收端处理不过来怎么办？这就需要发送方和接收方协商了。通常情况下，接收方会告诉发送方自己还可以接收多少数据，也就是接收窗口大小，并将其写在应答报文中。发送方收到应答报文后，会调整自己的发送窗口不超过接收窗口，避免数据丢失。

滑动窗口
蓝色和黄色区域即是滑动窗口的范围， 黄色窗口的数据可以继续发送

延申一个问题，发送窗口和接收窗口大小相等吗？ 从上边的介绍来看，接收窗口和滑动窗口似乎相等，但实际上并不是，接收窗口通过应答报文告知发送端，发送端调整自己的窗口，但应答报文的传输是有延迟的，所以两者并不严格相同。

流量控制

说到流量控制，先说下糊涂窗口综合征，接收端有多少空余缓冲，发送端就发送多少数据，即使只有1个字节的空闲空间。数据包的发送需要携带协议头，光TCP协议头最大可占16字节，再加上下层的IP协议头等，有效数据占比很低，这就是糊涂窗口综合征。

总结来说，糊涂窗口综合征就是通信双方频繁发送和接收小数据包

解决糊涂综合征的方法就是流量控制，从两个方面考虑：

  • 禁止接收方通告小窗口：接收方会设置一个最小通告窗口，低于这个阈值，直接告知发送方窗口为0
  • 禁止发送方发送小数据： 采用Nagle算法，数据累积到一定大小再发送

在低延时场景中，需要禁用Nagle算法，因为其增加了发送时延

接收方通报窗口为0后，发送方停止发送数据，直到接收端通报窗口非0。如果网络发生阻塞，窗口非0的ACK报文丢失，那不完蛋了，ACK报文丢失不会重传，那发送端不是一直不能发送数据了吗。
其实不然，发送端接收到窗口为0的应答报文后，会启动一个定时器，定期向接收端发送窗口探测报文，以此避免ACK报文丢失带来的死锁问题。

拥塞控制

流量控制只是避免发送方将接收端缓冲区填满，但是无法感知网络情况。当网络发送拥塞时，TCP 会自我牺牲，降低发送的数据量，这就是拥塞控制。和接收窗口不同，这里叫做拥塞窗口，会根据网络的拥塞程度动态变化的。

拥塞控制

拥塞窗口越大，可发送的数据越多。

拥塞控制分为四个阶段：

  1. 慢启动：拥塞窗口每收到一个ACK指数级递增
  2. 拥塞避免：当拥塞窗口大小超过慢启动门限，每收到一个ACK线性递增
  3. 拥塞发生：当出现数据包重传，进入拥塞发生阶段
    • 超时重传：慢启动门限重置为当前窗口的一半，窗口大小置为1
    • 快速重传：慢启动门限和窗口大小均置为当前窗口大小的一半
  4. 快速恢复：快速恢复结合快速重传一起使用，拥塞发生调整慢启动门限和窗口大小后，窗口呈线性增长

为什么超时重传和快速重传在拥塞发生阶段的处理不同呢？
快速重传说明收到了三个相同的ACK，既然网络还能传输这三个ACK，说明情况还没有太差，不必像超时重传那样一夜回到解放前。处理方式更加平滑。

延申一个知识点：IP层会进行数据分片，那传输层为什么还要分片，每片不大于MSS呢？
IP层分片是为了保证数据报文能够在网络上传输，假如传输层不进行分片，那某一个IP分片丢失，分片所在的整个数据块都要重传，效率很低，所以在传输层分片，重传的单位是MSS。
