异常


Exception和Error都继承自Throwable类，Exception属于程序本身可以处理的异常，可以通过catch捕获并处理；Error也可以通过catch捕获，但并不推荐这么做，比如OOMError内存溢出，捕获之后整个系统都会在高风险下运行

Exception进一步可分为受检查异常和非受检查异常，受检查异常必须抛出，否则编译无法通过，比如I/O相关异常或SQL异常等，非受检查异常又叫做运行时异常，包括RuntimeException及其子类，比如NPE、越界异常等

try-catch-finally

finally中的代码一定会执行，catch块个数可以为0或多个，但是为0时，必须使用finally代码块

try-catch-finally语法之所以finally一定会被执行，从字节码层面来看，是因为finally代码块的字节码通过冗余代码的形式在try和每个catch之后都嵌入

为了提高泛型的灵活性，支持协变和逆变，引入了通配符.

通配符有一个PECS规则:

  • 上界通配符只能get
  • 下界通配符只能add

下界通配符只能add

内存屏障

Java 通过 happens-before 关系定义操作间的可见性和顺序。内存屏障是实现这些规则的底层手段，主要用于禁止指令重排序和保证内存可见性。

在现代多核 CPU 和编译器优化下，程序执行可能被 重排序（Reordering），以提升性能，内存屏障的作用就是禁止某些重排序，并强制刷新缓存，确保“happens-before”关系成立

常见 happens-before 规则包括：

  • 程序顺序规则（单线程内按代码顺序）
  • volatile 变量规则
  • synchronized 锁规则

synchronized与内存屏障

happens-before规则：对同一个监视器（monitor）的解锁操作happens-before 后续对该监视器的加锁操作

  • 进入 synchronized 块（加锁）:
    线程 A 进入 synchronized 块之后，能够看到线程 B 进入同一 synchronized 块后的所有写操作
    • 相当于 LoadLoad + LoadStore 屏障（类似 volatile 读）。
    • 清空本地缓存，从主存重新加载共享变量。
  • 退出 synchronized 块（解锁）：
    线程 A 退出 synchronized 块之前的所有写操作，对线程 B 进入同一 synchronized 块之后的操作可见
    • 相当于 StoreStore + StoreLoad 屏障（类似 volatile 写）
    • 将本地修改刷新到主存。
      因此，synchronized 不仅提供互斥，还提供完整的 内存可见性保证
屏障类型 作用
LoadLoad 确保第一个 Load 在第二个 Load 之前完成
StoreStore 确保第一个 Store 在第二个 Store 之前完成
LoadStore 确保 Load 在后续 Store 之前完成
StoreLoad 确保 Store 在后续 Load 之前完成（最昂贵，常需刷新 store buffer）

反射

反射允许程序在运行时动态地修改或访问自身行为。为什么需要反射？在常规编程中，我们写代码时必须知道：

  • 要调用哪个类？
  • 要调用哪个方法？
  • 方法参数是什么？

以上三个条件是在编译时已知且固定的。但有些场景，这些信息是运行时才知道的，举个例子，JSON 库（如 Jackson）如何把字符串转成任意对象，转换的对象只有在运行到该逻辑之后才是已知的。反射就是在不知道具体类型的情况下，动态操作对象。反射是把双刃剑，虽然灵活性很强，但是也带来了以下问题：

  • 安全性差：通过反射可以访问私有变量和私有方法，破坏封装性
  • 性能较差：反射调用比直接调用慢，因为多了一步解析操作，可以通过缓存减少反射带来的性能损耗
