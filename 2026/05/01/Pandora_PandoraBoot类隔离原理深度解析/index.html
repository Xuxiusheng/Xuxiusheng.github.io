Pandora/PandoraBoot类隔离原理深度解析

依赖冲突

相信大家在服务启动时肯定遇到过各种各样的依赖冲突问题，轻则启动报错、功能异常，重则导致服务完全无法上线。那么，依赖冲突问题究竟是如何产生的呢？

简单来说，根本原因在于 Java 的类加载机制 与 Maven 等依赖管理工具的传递性依赖特性 共同作用下的结果。具体可以拆解为以下几点：

  • JVM 类加载机制：一个ClassLoader内部只能存在唯一一个类，不允许重复类存在（全限定类名相同）
  • Maven依赖传递：当你在项目中引入一个中间件或开源库时，它自身又会依赖其他库（传递依赖）。随着项目规模变大，依赖树会变得极其复杂，其中难免有不同的组件依赖同一个jar包的不同版本。Maven 虽然会按照“最短路径优先”或“最先声明优先”等规则自动仲裁选择一个版本，但这个版本可能并不兼容另一方，导致运行时报错。

在 Java 中，一个类的“全限定名”（如 com.example.User）并不足以唯一确定一个类。真正确定一个类的是：全限定名相同 && ClassLoader相同。

如果允许同一个 ClassLoader 加载两个同名类，那么当代码 new User() 时，JVM 会陷入混乱：到底该实例化哪一个？类型检查（如 instanceof）也会失效。

既然依赖冲突根源于类加载机制，那么解决方案自然也离不开类加载机制。在正式介绍 Pandora 之前，我们不妨先来看一个大家更熟悉的例子：Tomcat，看看它是如何解决 Web 应用之间的类冲突问题的。

Tomcat应用依赖隔离

Tomcat以单一JVM进程托管多个应用，不同应用之间依赖的三方库版本存在差异，在服务加载时，其实Tomcat会保留冲突依赖的版本，那它是怎么做到全限定类名相同的jar包共存于同一个JVM进程的呢？

答案是隔离ClassLoader并打破双亲委派模型。先看下Tomcat类加载器的拓扑图，它并没有把所有类都隔离，而是在原先的三层类加载器之下，又引入了两层类加载器层级：

  • CommonClassLoader：加载应用共享类，避免每个应用都重复加载相同的容器基础类
  • WebAppClassLoader： 应用独有，负载加载自身业务代码和私有依赖

隔离 ClassLoader 是指不同的业务应用拥有专属的 ClassLoader，真正实现了依赖冲突的隔离，而进一步打破双亲委派模型则是为了提高安全性和隔离性。具体过程如下：

  • 检查缓存：查看当前 ClassLoader 是否已经加载过这个类。如果已加载，直接返回缓存的 Class 对象
  • 检查是否属于 JVM 系统类（防止覆盖核心类）：如果类名以 java.、javax.、sun. 等开头，说明是 JDK 核心类，直接委派给父加载器（最终到 Bootstrap ClassLoader），不允许子类覆盖
  • 在自己的局部资源中查找（打破双亲委派的关键）：在当前 Web 应用的/WEB-INF/classes/ 目录和 /WEB-INF/lib/*.jar 文件中查找类。这一步先于父加载器执行，与标准双亲委派模型相反。如果找到了，由 WebappClassLoader 自己加载并返回
  • 在自己的局部资源中没找到，向上委托给父加载器

如果仅仅依靠类加载器隔离，而依然严格遵循双亲委派模型，是否能实现隔离呢？在这种情况下，所有的类加载请求都会优先向上委托给父类加载器。由于父类加载器（如 Common ClassLoader 或 AppClassLoader）的类路径中并没有各个 Web 应用特有的 Jar 包（WEB-INF/classes与WEB-INF/lib），这些请求在经过父类加载器查找并失败后，最终还是会由各个 Web 应用自己的 WebappClassLoader 来加载。但这是在理想条件下。还存在以下几个问题：

  • 虽然最终也能实现隔离，但每个类在加载过程中都多了一次不必要的父类加载器查找开销，这就会明显拖慢应用的启动速度。而打破双亲委派模型，正是在避免这种无意义的委托，让应用能直接在自己的局部资源中加载所需类，从而提升启动效率。

  • 安全性差，如果不打破双亲委派模型，那应用每一次加载都要委托父类加载器，WebAppClassLoader的父加载器是CommonClassLoader，再往上是SystemClassLoader，两者分别加载tomcat/lib和classpath下的jar包，如果这两个路径中存在与WebAppClassLoader要加载的类同名并且版本冲突，那WebAppClassLoader就会使用冲突的版本，而不是应用指定的版本。安全性无法由WebAppClassLoader自己来保证，行为不可预期，安全性差。

依赖隔离的底层本质，就是通过不同的 ClassLoader 实例，加载同名但实现可能不同的类，从而在 JVM 层面实现真正的隔离。但Tomcat实现的是业务应用之间的依赖隔离，同一个应用内部会依赖很多中间件，中间件也依赖大量jar包，中间件依赖jar包之间与业务直接依赖的jar包与中间件依赖的jar包之间也会存在冲突，Pandora/PandoraBoot就是解决这类应用内部的依赖冲突问题，粒度相比应用之间更加细粒度。

最后扩展一点：双亲委派模型不是万能的，在某些情况下必须打破，比如依赖隔离这里就是必须打破的。还有一种缺陷是子加载器可以看到父加载器可加载范围的类，但父加载器却看不到子加载器加载范围的类。 这里只简单举个例子：java中有个名词叫SPI接口，简单来说是java提供接口定义，具体的实现由外部厂商实现，注意和API进行区分。比如java.sql.Driver是一个SPI，由启动类加载器加载，com.mysql.jdbc.Driver是一个实现类，由AppClassLoader加载。在创建数据库连接时，需要调用DriverManager去找到Driver的实现类，但DriverManager是由启动类加载器加载的，无法看到由AppClassLoader加载的Driver实现类。这种情况下是通过线程上下文类加载器去创建实例，然后DriverManager持有这个引用。

Pandora容器隔离

在深入 Pandora 容器之前，需要先了解其核心概念：sar包。

其中，plugins目录下存储依赖的中间件plugin目录。Pandora的类加载器体系如下：

  • bizClassLoader: 加载PandoraClientFactory类，所有与Pandora容器相关的操作都由PandoraClientFactory完成

  • PandoraClientFactory创建PandoraClassLoader，这个类加载器负责加载PandoraContainer容器类、PluginModule类以及SharedClassService类

  • PluginModule负责为每个plugin创建ModuleClassLoader，每一个中间件都有自己专属的加载器，因此实现了中间件之间的依赖隔离

每个plugin会通过export.index对外暴漏服务，并将类Class对象存储到全局缓存。应用或其他plugin可以使用export.index导出的服务。综上所述，当服务要查找一个类时，首先是查当前ClassLoader是否存在类对象，如果没有，走双亲加载模型，如果依然未找到，查全局缓存。
