Redis Set 源码分析：三态编码与内存优化

在使用 Redis 时，Set 可能是最”不起眼”的数据结构——SADD 加元素，SINTER 求交集，几十个元素的小集合用起来毫不费力。但如果你打开 OBJECT ENCODING 看一眼，会发现 Redis 并不是简单地在每个 Set 里塞一个哈希表：它有时返回 intset，有时返回 listpack，有时才是 hashtable。

Redis 7.2之前，Set只有intset和hashtable两种底层结构，7.2版本之后引入了listpack作为混合类型小集合的底层结构。

这背后是 Redis 最核心的内存优化哲学：一个数据结构的”最佳实现”不是绝对的，取决于它处于什么样的规模和包含什么样的元素。 小集合用哈希表是浪费，大集合用数组是灾难。Redis 的做法是让 Set 在三种内部编码之间自适应切换，处处体现着系统编程中”用少量 CPU 换大量内存（时间换空间）”的经典权衡。

设计问题：为什么需要三种编码？

在讨论代码之前，先想一个问题：如果 Redis 用一个统一的数据结构存所有 Set，会有什么问题？

用哈希表存一切，O(1) 的增删查确实快。但 Redis 作为内存数据库，内存即成本。一个普通的哈希表条目（dictEntry）在 64 位系统上是 24 字节（key 指针 8 + value 联合体 8 + next 指针 8），这还没算哈希桶数组本身的开销。你存一个 3 字节的字符串 “foo”，光是存储它的结构体就要 24 字节，再加上 SDS 字符串本身的内存，开销是数据的十倍以上。

但也不能一刀切用紧凑数组。数组在元素少时省内存（无指针开销），但在上千个元素时 O(N) 的查找会让 SISMEMBER 慢得不可接受。更何况 Set 的元素可以是任意字符串，纯整数数组根本存不了 “hello”。

Redis 的选择是把”用哪种数据结构”的决定延迟到运行时，通过两个维度的判断来动态选择：

判断维度 阈值配置 含义
元素是否全是整数？ 无配置（运行时判断） 是 → 优先考虑 intset；否 → listpack 或 HT
元素数量有多少？ set-max-intset-entries（默认 512） ≤512 且全整数 → intset
元素数量 + 单大小？ set-max-listpack-entries（默认 128）
set-max-listpack-value（默认 32B）		 都满足 → listpack；否则 → HT

综上，Set底层结构变更规则如下：

  • 小数据量（小于512）且均为整数：intset
  • 小数据量（小于128）且存在字符串：listpack
  • 大数据量：hashtable

没有万能的数据结构，只有最适配应用场景的数据结构，底层结构的升级是单向的，以避免底层结构频繁变换导致时间延迟。

listpack和intset的转化阈值不同根本在于intset通过二分查找数据，而listpack是线性搜索，所以转化阈值设置的相对较低。

Intset

intset 的自适应宽度设计

intset 是整个 Set 实现中最精巧的数据结构。它的设计动机很明确：如果几个整数就能完成任务，为什么要动用哈希表？

为什么 encoding 存字节数而不是枚举值？ 假设 encoding 存 0=INT16, 1=INT32, 2=INT64，每次计算”第 N 个元素的偏移地址”都需要走分支判断偏移量。直接存 sizeof(int16_t)=2 等值，偏移公式直接就是 offset = N * encoding，省掉分支判断，对热路径上的二分查找非常重要。

补充一点，redis内部存储统一使用小端序，绝大多数生产环境本身就是小端序。选择小端序可以让Redis在内存中处理数据时，无需进行额外的字节序转换，从而获得更好的性能。之所以需要统一字节序是为了跨平台兼容因为redis是一个分布式服务，同一个集群的机器节点字节序可能不统一，避免不同节点直接的数据解析错误。

  • 小端序的优势在于从低位开始计算的硬件效率，CPU可以在读取第一个字节后立即开始计算，无需等待所有字节加载完毕。在大端序下，则必须等待所有字节到达才能从高位开始运算
  • 网络传输采用大端序主要是历史原因，采用大端序可以在接收到头部数据后快速判断报文类型、长度等关键信息，因此当时的TCP/IP协议制定的时候采用了大端序

intset编码升级后需要将原始intset的已有数据和新数据写入到新的位置，升级扩容时是优先原地扩容。在移动数据时，是从后向前遍历，因为新旧编码宽度不同，正向遍历会导致写入位置覆盖尚未移动的旧数据。从后向前保证每个位置的源数据在被读取之前不会被新数据覆盖。
编码升级后插入新数据时不需要二分查找插入位置，因为新数据的插入位置只能是开头或者末尾，因为如果触发编码升级，一定是小于当前编码的最小值或者大于当前编码的最大值。

一个重要的设计选择：编码只升级不降级。 即使删除了导致升级的那个超大值，编码仍保留在 INT32。Redis 认为，降级需要遍历所有元素验证”是否还能用小编码”，然后重新分配和拷贝整块内存，CPU 代价不小。而实际生产环境中，留着一个稍大的编码多占几十到几百字节，比每次删除都去检查降级条件更划算。这是内存数据库经典的 tradeoff：省 CPU 就是在省延迟，而内存省到一定程度就够了。

Hashtable

dict 的 tagged pointer 零分配优化

当 Set 规模变大（超过 128 个元素或某个元素超过 32 字节），编码升级到 HT（哈希表）。Set 只需要 key（元素值），不需要 value。dict 为此实现了一套基于 tagged pointer 的存储优化：在负载因子 1.0 左右时，绝大多数元素的存储零额外分配。

C语言中如果一个指针指向NULL，其值为全0

理解 tagged pointer 之前，必须先看清 dict 的物理布局。dict 的核心是两张哈希表：

正常状态下只有 ht_table[0] 在使用，ht_table[1] 为空。当负载因子触发扩容时，ht_table[1] 被分配为更大的一张表，然后通过渐进式 rehash 逐桶将元素从 table[0] 迁移到 table[1]，完成后 table[1] 变成新的 table[0]。

每张哈希表本质上是一个 dictEntry* 类型的数组，数组的每个槽位（bucket）存一个指针，这个指针指向该桶上的链表：

bucket 指针指向一个 dictEntry 节点，节点之间用 next 指针串联：

一个 dictEntry 占 24 字节。对于一个 Hash 类型（HSET myhash field value），key 是 field，value 是实际的 value，两个字段都用上了，24 字节物有所值。

但 Set 不需要 value。如果 Set 也分配完整的 dictEntry，每个节点浪费了 8 字节的 v 联合体——1000 万个元素就是 80MB 的纯浪费。

64 位系统上，zmalloc 返回的地址至少是 8 字节对齐的，即任何有效地址的二进制最低 3 位永远是 000。这意味着在桶里存一个”指向 dictEntry 的指针”时，这个 8 字节值的低 3 位不参与表示地址。

Redis 的思路是：既然这 3 个 bit 在表示指针时用不上，就用它们来标记”这个桶里存的到底是什么”。读取时先看低 3 位，再决定如何解析这个 8 字节值。

状态 A：空桶

无关 tagged pointer。但正是因为很多桶是空的，哈希表才需要精心控制负载因子，空桶也是 8 字节的槽位。

状态 B：桶内只有一个元素（最常见，利用 ODD_KEY）

此时不分配任何 dictEntry。桶数组的 8 字节槽位直接存了 SDS 指针。为什么 SDS 指针天然 bit0 = 1？因为 sds 是 char* 类型，指向字符串内容的第一个字符；而 zmalloc 返回的原始地址是偶数（8 字节对齐），sds 结构在这之前有一个 1 字节的 header，所以 sds 指针 = 偶数 + 1 = 奇数。keys_are_odd = 1 告诉 dict “所有 key 的 bit0 已经是 1，不需要显式 | 0x1“。

状态 C：桶内有两个或更多元素（碰撞链）

dictEntryNoValue只含 key 和 next 两个指针，16 字节，比完整 dictEntry 的 24 字节省了 33%。而且碰撞链上的后续元素仍然可以走 ODD_KEY 零分配。

桶内元素数 实际内存布局 每个元素的平均开销
1 个 bucket 槽位直接存 SDS 指针（ODD_KEY） 0 字节
2 个 1 个 dictEntryNoValue（16B）+ 1 个 ODD_KEY 平均 8 字节
3 个 2 个 dictEntryNoValue（32B）+ 1 个 ODD_KEY 平均 10.67 字节
N 个（N≥2） (N-1) 个 dictEntryNoValue + 尾节点 ODD_KEY 16×(N-1)/N 字节

碰撞链的最后一个节点依然可以走ODD零分配，实际负载下，负载因子约 1.0 时绝大多数桶只有 1 个元素，碰撞比例极低——每个这样的桶享受完整的零分配。假设 1000 万元素分布在约 1000 万个桶中，不走 tagged pointer 需要 240MB 的 dictEntry 开销；优化后，单元素桶零开销，少量双元素桶仅有 16 字节，总 overhead 骤降到几 MB 级别。

Redis Set 的实现是内存数据库设计中”自适应“思想的典型案例。三态编码不是三个独立的数据结构，而是同一个逻辑集合在不同生命周期阶段的物理表达：

  • 新生期（INTSET）：纯整数、量小——用最紧凑的有序数组，二分查找够快，内存效率最大化
  • 成长期（LISTPACK）：混入字符串、量适中——用连续内存块，线性查找因为量小所以可接受
  • 成熟期（HT）：量大到一定程度——用哈希表保证 O(1) 操作，但通过 tagged pointer 避免 value 浪费
