Redis底层揭秘：内存分配与回收篇

内存泄漏？碎片率飙升？本文带你彻底搞懂 Redis 的内存分配与回收逻辑。从自定义分配器的设计初衷，到后台清理策略的实战影响，一文讲透如何驾驭 Redis内存。

Redis作为内存数据库，内存是其最宝贵的资源。在 Redis的源码世界里，你很难直接看到裸奔的 malloc/realloc/calloc/free。取而代之的，是一套严密的内存分配包装器。这是为了解决一个核心痛点：原生内存分配器缺乏可观测性。Redis 通过拦截所有的内存请求，在底层之上构建了一个统计仪表盘。正是这一层巧妙的封装，让我们能在 INFO memory 中看到实时的内存使用情况，让内存问题无处遁形。

分配篇

告别裸奔的malloc家族，Redis 推出了自己的内存管理四剑客：

  • zmalloc(size)：带计数的内存分配。
  • zcalloc(count, size)：带计数的清零分配。
  • zrealloc(ptr, size)：带计数的内存重分配。
  • zfree(ptr)：带计数的内存释放。

在 Redis 的内存分配调用链中，zmalloc仅负责上层的统计封装，而真正的核心分配逻辑下沉到了ztrymalloc_usable_internal。这个内部函数才是真正向操作系统‘伸手要内存’的角色。它不仅执行底层的 malloc 调用，还利用特定分配器（如 jemalloc）的特性，直接获取分配后的实际占用大小。这一步至关重要，因为它解决了统计精度问题。

在深入 ztrymalloc_usable_internal 的实现细节之前，我们先厘清内存分配器的核心概念。因为不同的分配器不仅决定了底层的内存布局策略，更直接定义了统计逻辑。

Redis 自身无法直接感知底层分配器内部的具体细节（如内部碎片），它只能依赖分配器提供的API来统计内存。不同的分配器提供的统计能力不同（甚至没有提供），导致 Redis 的统计策略必须因地制宜。

  • jemalloc/tcmalloc：提供了丰富的 API（如 malloc_stats_print, mallctl），能详细汇报内部状态。
  • libc (glibc malloc)：标准 C 库通常不提供细粒度的统计 API，只负责分配和释放。

出于性能优化的考量，现代分配器绝不会按需分配。为了满足内存对齐要求，往往会分配比请求值更大的内存块，由此产生的内部填充虽对用户不可见，却真实占用了物理空间。
关键差异在于：Jemalloc 等高级分配器提供了专用接口（如 je_malloc_usable_size），允许程序精准查询这块内存的实际占用大小；而部分传统分配器（如 glibc malloc）则缺乏此能力。
正是为了兼容这两种截然不同的统计机制，Redis 在底层实现了两套适配方案：在支持查询时追求绝对精准，在不支持时退化为估算模式，以确保内存监控在任何环境下都能稳定运行。

分配器会在元数据PREFIX中记录这个‘内存大小’。

  • 分配时：Redis 通过获取该值，将其计入内存水位。
  • 释放时：同样依据该值从统计面板中扣除，确保统计值完全匹配物理内存的真实流动

不同的内存分配器分配内存后，空间结构不同：

  • 如果内存分配器不支持API查询实际分配大小，redis会额外申请8字节的空间PREFIX，用于存储本次用户申请的空间（不包含内存碎片，所以统计不准确，只算是估算），统计水位变化时根据用户申请的空间变换，free时会读取PREFIX查询指针指向的空间大小（不包含内存碎片）
  • 如果内存分配器支持API查询实际分配大小，不需要额外的元数据PREFIX，并且统计水位变化时根据分配器实际申请的空间变换，free时会调用分配器API查询指针指向的空间实际大小

有几点需要注意：

  • glic分配器其实也支持实际内存分配查询，但在某些旧版本或特定场景下，它需要更多的锁竞争或复杂的计算，所以查询很慢，因此在glic分配器下，默认采用估算模式。
  • malloc的地址空间本身也有元数据，对用户不可见，所以在估算模式下，这部分元数据和内存碎片均没有被统计，只有PREFIX这个redis自定义的元数据被统计了

ztrymalloc_usable_internal 的使命纯粹而极致：只负责获取内存与量化大小。作为一个 static inline 函数，它被编译器直接‘内联’嵌入到调用现场。这种设计彻底消除了函数调用的栈帧开销，让每一次内存分配都像是在执行原生指令一样高效。

试想，若缺失了 Jemalloc 或 TCMalloc 这类支持‘实际占用查询’（malloc_usable_size）的现代分配器，Redis 将面临哪些风险呢？

  • 内存淘汰机制失效：Redis的 maxmemory限制是基于used_memory判断的，但估算模式下内存碎片未被计入统计面板，会导致淘汰机制触发滞后，严重情况下会触发OOM
  • 主动碎片整理功能强依赖 Jemalloc/TCMalloc，主动碎片整理功能将完全失效

综上所述，推荐使用jemalloc/tcmalloc等内存分配器。

如果真的条件不允许使用jemalloc/tcmalloc,那怎么办呢？

  • 调低 maxmemory，预留安全缓冲
  • 改用外部内存监控

zrealloc 与 zcalloc 严格遵循了与 zmalloc 相同的统计规则。它们本质上是对原生 realloc 和 calloc 的透明封装。

释放篇

Redis 的内存回收策略分为主动释放和被动淘汰：

  • 主动释放：源于用户的显式操或键的自然过期。直接调用 zfree 释放指针，并同步更新内存统计。
  • 被动淘汰：当内存占用触及 maxmemory 阈值时，内存淘汰机制被触发。依据预设算法，主动甄选并剔除部分‘低价值’数据，以腾出空间容纳新写入，防止 OOM 崩溃。

两者底层均基于zfree释放空间。 zfree 的实现非常简洁，其核心逻辑依据分配器是否提供统计API进行了区分：

  • 精准模式（支持 malloc_usable_size）：在释放指针前，先调用接口获取该内存块的实际物理占用大小，从全局统计中精确扣除这一数值，随后再执行原生 free。这确保了借多少还多少。
  • 兼容模式（不支持查询）：若分配器无法提供实际大小，则退化为直接调用原生 free。此时统计系统仅能基于先前记录的‘用户请求大小’进行扣除（free释放时是释放实际分配的物理内存，只不过用户无感知）。

之所以使用zfree，不仅是为了保证统计面板的变化准确，也是为了确保内存的正确释放，因为在内存分配器不支持精确查询的情况下，分配内存时真正的起始指针是元数据的起始指针，而不是用户数据。
