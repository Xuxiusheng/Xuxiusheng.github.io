Redis底层揭秘：SDS

编码格式

在Redis中，字符串是用户最常接触的数据类型。无论是键值对的 Key 与 Value，还是底层通信协议的缓冲，字符串无处不在。Redis 并没有直接使用 C语言原生的字符串，而是自研了一套名为 SDS（Simple Dynamic String，简单动态字符串） 的抽象结构，解决 C 字符串在性能、安全性和功能上的诸多缺陷，为 Redis 的高性能奠定了坚实基础。

在C语言的内存模型中，整数类型的uint8_t仅需 1 字节，而uint64_t则占据 8 字节。为了实现对内存的极致利用，Redis为SDS设计了五种不同的头部结构。它们通过不同的元数据字段大小，来适配从极小字符串到超大字符串的各种场景。这是按需分配，以空间换时间思想的经典体现

sdshdr8至sdshdr64的结构设计保持一致，主要区别在于len和 alloc字段的位宽不同。其中，len字段记录 SDS字符串长度，而 alloc 字段则记录分配的总可用空间。这两个字段的数值均不包含 SDS 头部本身的大小。flags字段用于表示当前的编码格式:

sdshdr5 的结构设计比较特殊，专为存储极短的字符串（长度小于 32 字节）而优化。为了极致压缩内存占用，其头部仅包含一个 flags 字段，不再单独设置 len 和 alloc。该 flags字段的低3位用于标识 SDS 类型，高5位则直接用于存储字符串的长度信息。在其他编码类型中，flags的高5位无意义。

SDS vs. C语言原生字符串

SDS的优势主要有四个：

  • O(1)获取长度：SDS 在结构体中通过len字段直接记录字符串长度，无需像 C 字符串那样遍历整个数组直到遇到 \0，将时间复杂度从 O(N) 降为 O(1)。
  • 二进制安全：SDS 不依赖 \0 作为结束标志，而是通过 len 字段界定边界，因此可以安全地存储包含空字符的二进制数据（如图片、序列化对象）。
  • 空间预分配：在字符串增长时，SDS会分配额外的未使用空间，避免频繁修改字符串时反复执行内存重分配。
  • 杜绝缓冲区溢出：SDS API 在执行修改操作前，会自动检查剩余空间。如果空间不足，会先自动扩容，彻底消除了 C 字符串常见的缓冲区溢出风险。

接下来通过三个核心底层函数来一探究竟：_sdsnewlen、_sdsMakeRoomFor以及sdscatlen。

  • _sdsnewlen：这是所有字符串创建接口的底层接口
  • _sdsMakeRoomFor：这是处理字符串扩容的底层接口
  • sdscatlen：字符串拼接接口

通过上述代码，我们可以清晰地观察到 SDS 的空间预分配策略：

  • 当目标长度小于 1MB 时，系统会采用翻倍增长（newlen *= 2）的机制。这种指数级的扩容方式，有效减少了在连续追加字符串时的内存重分配次数，但可能存在大量内存碎片
  • 对于超过 1MB 的大字符串，SDS转为采用线性扩容策略，每次固定增加 1MB 的空间（newlen += 1MB）。这种设计避免了在处理大数据量时，因盲目翻倍而导致的内存浪费。

预分配策略仅应用于扩容阶段。在 SDS 的初始化阶段，内存分配遵循按需分配原则，即申请多少便分配多少。这是因为在创建字符串时，系统尚无法预知后续是否会有追加操作以及具体的增量大小。此时若盲目进行预分配，反而会导致不必要的内存浪费。

接下来将目光转向 sdscatlen 接口，一探Redis是如何从根本上杜绝缓冲区溢出问题的。

在执行字符串拼接操作之前，Redis 会优先调用扩容接口（sdsMakeRoomFor），对剩余空间进行校验。只有当确认空闲空间足以容纳新增数据时，才会执行后续的写入操作，从而从机制上确保了存储的安全性。

SDS针对性优化

为了统一管理数据形态，Redis 在底层设计了一个通用的redisObject（robj）结构体。它是一个标准化的容器，将字符串、列表、集合等截然不同的数据类型进行了统一封装。如果robj内部存储的是字符串，在正式执行命令之前，会经历一次针对性的内存优化流程，而这一任务是由tryObjectEncodingEx函数负责。它会尝试将字符串转换为更紧凑的内部编码（如整数编码或嵌入式字符串），从而在存储层面最大限度地节省内存。

tryObjectEncodingEx是检查默认编码的robj能否转换为更节省内存的编码格式。

接下来聚焦于从 RAW 到 EMBSTR 的转化过程。这一步是 Redis 内存优化的关键所在，它通过将 redisObject和 sds 合并到同一块连续内存中（更加有利于局部访问命中），将两次内存分配简化为一次，显著提升了小字符串的存储效率。

先对比一下redisObject这两种模式的内存结构：

  • RAW格式：当创建一个普通字符串对象时，Redis需要进行两次内存分配：
    • 分配 redisObject：存放对象的元数据（类型、引用计数等）。
    • 分配 sds：存放实际的字符串数据。
  • EMBSTR：一次分配，将 redisObject 和 sds 分配在同一块连续的内存中

OBJ_ENCODING_EMBSTR_SIZE_LIMIT默认为44，主要是为了兼容jemalloc
