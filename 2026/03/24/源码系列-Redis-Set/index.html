源码系列-Redis Set

底层结构

Redis Set底层存在两种编码方式：intset与hashtable，当元素数量未超过设定阈值（默认512）并且均为整数，使用intset，否则使用hashtable。

intset的整数编码有三种方式：int16、int32和int64，当encoding为int16时，contents每两个元素表示一个数值，其他两个依次类推

源码解析

intsetAdd 的流程就是：

  • 先判断新值需要几字节
  • 如果当前编码不够，升级整个集合并插入
  • 如果编码够，就二分查找
  • 已存在则直接返回
  • 不存在则扩容、挪尾巴、写入新值、长度加一
  • 插入成功后，判断当前set元素数量是否超过配置阈值，超过则将intset转化为hashtable

SINTER操作有一个小优化：对所有set按照元素数量从小到大排序再取交集，有以下两点优势：

  • SINTER操作是以第一个set为基准，依次拿元素去其他集合判断是否存在，所以，元素数量越少，需要判断的元素越少
  • 先小后大，通过SISMEMBER操作判断是否存在该元素，intset编码方式下，该操作为O(logN)时间复杂度，所以先判断数量少的集合，如果没有直接跳出判断基准set的下一个元素

intset 是有序数组，不是哈希表，所以插入不是 O(1)，查找是 O(logN)，搬移尾部最坏 O(N)。

只有“需要升级编码”时，才不必查重，因为这说明新值超出了旧编码范围，不可能已经存在。

注意，redis hashtable不需要控制并发，因为redis是单线程模式运行。

从上边分析可以看出，sadd命令有许多重型操作：

  • intset升级转hashtable
  • intset整数编码格式升级
  • 数据插入删除

所以和list一样，大key问题需要注意

此外，还需要注意，当set底层为intset时，并没有空间预分配策略，存储多少元素就精确分配多少空间，所以如果是在频繁写set的场景下，短期内会有内存瓶颈，当intset超过阈值转化为hashtable后，hashtable有自己的扩容策略。
